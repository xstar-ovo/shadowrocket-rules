# 📱 极简配置 + 模块的搭配方式（防 IPv6 / DNS 泄露）

本文对应仓库根目录的 [`tiny_rules.conf`](../tiny_rules.conf)（白名单模式）与 `sr_direct_list.module` / `sr_reject_list.module` 的组合用法。
适用于 iOS 上 Shadowrocket（小火箭），目标是：**该走代理的都走代理，同时不把域名解析、IPv6 流量漏给本地网络**。

> [`03.shadowsocks_tiny.conf`](./03.shadowsocks_tiny.conf) 是上游作者的原版配置，每日构建会连带刷新它，**不要修改它**。`tiny_rules.conf` 是在它基础上加固的自用版，独立维护，上游更新不会覆盖。两者差异见第九节。

## 一、这套组合由什么构成

| 层 | 用哪个 | 说明 |
| :--- | :--- | :--- |
| 配置 | [`tiny_rules.conf`](../tiny_rules.conf) | 从上游 03 复制再加固：白名单 `GEOIP,CN,DIRECT` + `FINAL,PROXY`，外加一段个人直连偏好。**只需要维护这一个配置文件** |
| 模块（第 1 位） | **`sr_direct_list.module`** | 必须。11 万条国内域名直连，天花板规则 |
| 模块（第 2 位） | `sr_reject_list.module` | 可选。20 万条广告/统计域名，不要就更省内存 |
| 模块 | ~~`sr_proxy_list.module`~~ | **不要加载**，原因见第三节 |

## 二、三条硬性规则

1. **配置只能有一个生效**。远程配置和本地配置不要同时用，导入后删掉另一个。
2. **模块顺序：直连在上，屏蔽在下**。模块中的规则优先于配置中的规则；多个模块之间，上面的优先于下面的。
3. **个性化规则做成自建小模块放最上面**。被模块覆盖掉的特殊规则，写进自己的模块并拖到第一位，就自然生效了。

## 三、为什么白名单模式不需要 `sr_proxy_list.module`

规则是**从上往下**匹配，先命中者生效。白名单模式的最后一条是 `FINAL,PROXY`，**所有没被上面命中的连接默认进代理**。而 `sr_proxy_list.module` 里那 2.7 万条 `,PROXY` 规则，结论和 `FINAL,PROXY` 完全一致——它的用途是给「`FINAL,DIRECT` 黑名单模式」挑出被墙站点。

不加载它还有两个好处：

- 里面**有 15 条 `IP-CIDR` 没有写 `no-resolve`**。域名请求一旦遇到 IP 类规则，小火箭会先向本地 DNS 查一次才判断是否匹配（见 [01.shadowrocket_configure.md](./01.shadowrocket_configure.md) 中 `no-resolve` 的说明）——正是我们要避免的行为。
- 它会把一些本该直连的域名改成走代理（下载站、CDN、软件更新服务器等），白名单模式下没有必要。

> 唯一会出问题的场景：某个被墙域名的数据错误地被写进了直连表。加载 `sr_proxy_list` 也救不了（直连模块在上面，一样优先），正确做法是在自建模块里补一条 `DOMAIN-SUFFIX,xxx.com,PROXY`。

## 四、个人规则写在哪里

全部写进 `tiny_rules.conf` 的 `[Rule]` 段，**不要另外维护第二份配置文件**（例如网上流传的完整版 `default.conf`）。两份配置同时存在时只有一份生效，规则还会互相矛盾，后续排错会非常痛苦。

`[Rule]` 段分三块，从上到下：

1. **个人直连偏好**（约 170 条，`DOMAIN-SUFFIX,xxx,DIRECT`）：可直连但走代理会变慢、或走代理会丢掉机构 IP 授权的站点（Steam、Apple/Windows 更新、学术库、私有 tracker 等）。整段删掉不影响分流正确性，只是这些站点会退回 `GEOIP` / `FINAL` 判断。
2. `GEOIP,CN,DIRECT`（可选）。
3. `FINAL,PROXY`。

要新增偏好，就加在第 1 块里；要临时把某个被墙站点改走代理，加一行 `DOMAIN-SUFFIX,example.com,PROXY` 放最上面即可。

> 配置里的规则永远排在模块之后，因此直连表已收录的域名加 `DIRECT` 是没意义的（本来就连），但加 `PROXY` 同样无效——这类情况只能在上面提到的自建模块里覆盖。

## 五、配置逐项说明

| 键 | 值 | 为什么这么写 |
| :--- | :--- | :--- |
| `dns-server` | `https://1.1.1.1/dns-query#proxy, https://8.8.8.8/dns-query#proxy` | 用 **IP 形式**避免「先明文解析 DoH 服务器域名」；`#proxy` 让查询本身经节点转发，绕开 1.1.1.1 / 8.8.8.8 的 443 在大陆不可达的问题 |
| `fallback-dns-server` | `https://1.0.0.1/dns-query#proxy` | 覆写 DNS 失败时回退。**留空或写 `system` 等于回退运营商明文 DNS**，这是最常见的泄露点 |
| `dns-direct-system` | `true` | 只影响「已判定直连」的国内域名，用系统 DNS 就近解析。DNS 覆写只作用于直连域名，代理域名一律由节点远端解析 |
| `dns-direct-fallback-proxy` | `true` | 直连域名解析失败时改走代理，纯可用性，与泄露无关 |
| `ipv6` / `prefer-ipv6` | `false` | 不启用 IPv6，v6 内容流量进 tun 后无路可走 |
| `udp-policy-not-supported-behaviour` | `REJECT` | 节点不支持 UDP 时直接拒绝而不是直连，堵住 v6 的 UDP 绕行 |
| `skip-proxy` / `tun-excluded-routes` | 局域网网段 | 本地设备、投屏、mDNS 不经过小火箭 |
| `[MITM] enable` | `false` | 本项目的三个模块是纯规则，不需要解密；只有在用脚本类模块时才需要开 |

DNS 的域名字段里不要出现 `dns.alidns.com`、`119.29.29.29` 这类大陆解析器，也不要写 `system`。

## 六、`GEOIP,CN,DIRECT` 要不要留

| 选择 | 效果 | 代价 |
| :--- | :--- | :--- |
| **保留**（默认） | 直连表里没有的国内新域名也能直连，不绕道海外 | 未命中域名的连接会先做一次本地解析（经节点 DoH，不外泄，多一次延迟） |
| **删掉** | 一条本地解析都不发生，最干净 | 直连表外的国内域名会被 `FINAL,PROXY` 送去绕地球，可能变慢 |

想让国内域名连明文 DNS 都不走，就把 `dns-direct-system` 改成 `false`：此时直连域名也经 `#proxy` 的 DoH 解析，运营商看不到任何查询，代价是部分国内站点会解析到海外 CDN 节点，速度变慢。

## 七、生效后怎么验证

1. `小火箭 -> 数据 -> DNS 日志`：服务器应只有 `1.1.1.1`、`8.8.8.8`、`1.0.0.1`，加上国内域名的系统 DNS 那一条。出现 `223.5.5.5`、`119.29.29.29`、运营商地址、路由器地址 → 还有泄露。
2. 打开 `ipleak.net` 或 `dnsleaktest.com`（Extended test）：解析器应为节点机房或 Cloudflare / Google。
3. 打开 `test-ipv6.com`：不应拿到 IPv6 地址（`ipv6 = false` 下这是正常表现，不是故障）。
4. `小火箭 -> 数据 -> 代理`：访问国内站点时不应出现大量 `CONNECT` 记录。

## 八、常见问题

- **某个国内站点变慢/打不开**：它没进直连表。自建模块里加 `DOMAIN-SUFFIX,example.com,DIRECT` 并放到最上面。
- **某个被墙站点打不开**：检查是不是被直连表误收录，自建模块里加 `DOMAIN-SUFFIX,example.com,PROXY`。
- **DNS 日志里全是超时**：`#proxy` 的查询依赖节点能转发 TCP。节点用纯 UDP 协议或节点不可用时，先确认节点本身能上网。
- **想要黑名单模式**：加载 `sr_proxy_list.module`，配置改成 `FINAL,DIRECT`。此时才需要这份 2.7 万条的代理表，但同时要接受那 15 条 `IP-CIDR` 带来的本地解析。
- **规则太多很卡**：不加载 `sr_reject_list.module`，能省 20 万条规则的编译与内存。
- **上游每日更新**：本项目每天自动构建模块并刷新 `README.md`、`docs/00`、`docs/03`。你只需要 `git pull --rebase`，`tiny_rules.conf` 与本文档不会被覆盖；上游若新增了加固项，用第九节的对照表决定要不要跟进。

## 九、与上游原版 03 的差异

| # | 上游 `docs/03` | `tiny_rules.conf` | 原因 |
| :--- | :--- | :--- | :--- |
| 1 | `dns-server = system`、`fallback-dns-server = system` | 两个 IP 形式 DoH + `#proxy`，回退同样是加密 DoH | `system` 就是运营商明文 DNS，直连域名的解析直接暴露给本地网络 |
| 2 | `ipv6 = true` | `false` | 要求不泄露 v6；开启后部分 v6 内容流量可能绕过节点从物理网卡直出 |
| 3 | `dns-direct-system = false` | `true` | DNS 覆写全在海外，直连域名也被海外解析会让国内站点拿到海外 CDN IP |
| 4 | `dns-direct-fallback-proxy = false` | `true` | 可用性 |
| 5 | 无 UDP 策略 | `udp-policy-not-supported-behaviour = REJECT` | 配合 `ipv6 = false` 堵住 UDP 绕行 |
| 6 | 无 `[Host]` / `[MITM]` | 补上，MITM 保持关闭 | 完整性；纯规则模块无需解密 |
| 7 | 无个人偏好规则 | 170 条 `DOMAIN-SUFFIX,…,DIRECT` | 直连模块未收录的站点，其中学术库走代理会丢失机构 IP 授权 |
| 8 | `bypass-system = false` | 同上游 | 保持不动：Apple Intelligence / Siri 的 ChatGPT 扩展依赖系统守护进程走代理 |

> 上游把 `ipv6` 打开是为了支持 IPv6 网络，而本配置优先保证不泄露。若你更认同上游的取舍，改回 `ipv6 = true` 即可，代价是 v6 内容可能不经节点直连。
